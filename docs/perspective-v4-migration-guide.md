# Perspective v4.5.1 Migration Guide

This document is the executable plan for upgrading the dashboard's Perspective
dependency from `@finos/perspective ^3.8.0` to `@perspective-dev/* 4.5.1`. It is
the companion to [ADR-031](adr/ADR-031-perspective-v4-upgrade.md), which records
the architectural decision; this guide records how to execute it.

All package names, versions, plugin names, and API claims below were verified
against the npm registry and the actual `4.5.1` tarballs before this guide was
written — they are not assumptions.

## 1. Research Summary (verified)

Starting with version 4.0, Perspective moved from the `@finos` scope to the
`@perspective-dev` scope as part of its move into the OpenJS Foundation. The old
packages stop at `3.8.0`; **no 4.x release was ever published under `@finos`.**

Verified facts:

- **Scope change**: `@finos/*` → `@perspective-dev/*`. `@finos/perspective` latest
  is `3.8.0`; `@perspective-dev/client@4.5.1` exists on npm.
- **`"Datagrid"` plugin** is registered by `@perspective-dev/viewer-datagrid`
  (confirmed: `name:"Datagrid"` in the bundle).
- **`"Heatmap"` plugin** is registered by `@perspective-dev/viewer-charts`
  (confirmed: `"Heatmap"` string literal + `heatmap.frag/vert.glsl` shaders; the
  package is described as "Perspective.js WebGL Plugin").
- **`d3fc` is stale, not deleted.** `@perspective-dev/viewer-d3fc@4.4.1` still
  exists but lags `4.5.1`; the `"Heatmap"` plugin moved to the WebGL-based
  `viewer-charts`. The recommended mapping is therefore `d3fc → viewer-charts`
  (deprecated in favor of, not hard-replaced by).
- **`<perspective-viewer>` custom element name is preserved** in v4.
- **Core API is compatible**: `@perspective-dev/client` exports `worker` (named),
  and `table()` accepts `Record<string, unknown>[]` — exactly the array-of-objects
  shape the three components pass.
- **WASM asset renamed**: v3 served `perspective-client.wasm`; v4 ships
  `perspective-js.wasm` plus `perspective-server.worker.js`. This is relevant to
  the dev-server WASM issue recorded in
  [ADR-015 §Known limitations](adr/ADR-015-analytics-dashboard-wiring.md).

- `frontend/components/charts/CorrelationMatrix.tsx`

- `frontend/__tests__/components/charts/LiquidityHeatmap.test.tsx`

A repo-wide grep confirms these eight are the complete set — no other file
references Perspective.

## 3. Risks (read before executing)

1. **v4's packaging is incompatible with Next 16's default Turbopack.** v4 boots
   its worker via a runtime `Blob`-URL `import()`, and its dist references
   `src/*.ts` by `.js`. Turbopack errors on the first (`Can't resolve ('null' |
   <dynamic>')`) with no workaround. **Resolved by switching the dashboard to
   webpack** (`next dev`/`next build` `--webpack`) plus the `next.config.ts` in
   Step 6. See [ADR-031](adr/ADR-031-perspective-v4-upgrade.md) for the full
   rationale; this is the single non-mechanical part of the migration.
2. **Unit tests cannot prove the migration works.** Every component spec `vi.mock`s
   Perspective out, so `npm run test` only proves the import paths rewired
   correctly — it cannot catch WASM-load, worker-init, theme, or render failures.
   A dev-server smoke test (Step 6) is the real gate for those.
3. **CSS/theme system was redesigned in v4.** v4 ships ~12 theme files under
   `dist/css/`. The components import no Perspective CSS today; v4 may need an
   explicit theme import. Check during Step 6 and record in ADR-031 if so.
4. **This is a major version bump (3 → 4).** A changelog pre-check (Step 1) guards
   against breaking changes beyond package names that the component code does not
   exercise today.

## 4. Implementation Plan

### Step 0 — Record the decision (ADR-031)

[ADR-031](adr/ADR-031-perspective-v4-upgrade.md) documents the scope change, the
`d3fc → viewer-charts` rationale, and the Next/WASM-loading risk as an accepted
consequence. Done before any code change so the rationale survives the diff.

### Step 1 — Changelog pre-check

Read the Perspective v3 → v4 migration/breaking-changes and confirm, for the
narrow API the three components use, that nothing changed beyond package names:

- `worker()` factory signature.
- `table(objects[])` schema inference from an array of plain objects.
- Attribute names: `row-pivots`, `columns`, `sort`, `plugin`.
- Whether a CSS/theme import is now mandatory.

Record any deviation in ADR-031 and adjust Step 3 before editing.

### Step 2 — Atomic dependency swap

Edit `frontend/package.json` directly: replace the four `@finos/*` lines with the
four `@perspective-dev/*` entries at `^4.5.1` (caret, matching the existing v3
convention). Then run, from `frontend/`:

```bash
npm install
```

This regenerates `package-lock.json` and avoids the broken-tree window that a
separate `npm uninstall` followed by `npm install` creates. Sanity-check:

```bash
git diff frontend/package.json frontend/package-lock.json   # only the 4 packages changed
```

### Step 3 — Mechanical refactor (six files)

Replace the four specifiers **in the six code files only** (do not blanket-replace
repo-wide — the eight-file scope is already complete):

- `@finos/perspective` → `@perspective-dev/client`
- `@finos/perspective-viewer` → `@perspective-dev/viewer`
- `@finos/perspective-viewer-datagrid` → `@perspective-dev/viewer-datagrid`
- `@finos/perspective-viewer-d3fc` → `@perspective-dev/viewer-charts`  *(Heatmap plugin)*

The `vi.mock` shapes in the three test files are unchanged (`{ worker: vi.fn(...) }`
remains valid — `worker` is a named export in v4). After editing, confirm no stray
references remain:

```bash
grep -rn "@finos/perspective" frontend --include="*.ts" --include="*.tsx"   # expect: no matches
```

### Step 4 — Static gates

```bash
cd frontend
npm run typecheck   # tsc --noEmit — the real type gate
npm run lint        # eslint — advisory per project conventions
```

### Step 5 — Unit tests

```bash
npm run test
```

All three component specs should pass unchanged (they assert panel render +
empty-state; mocks are mechanical). Green here proves wiring, not rendering.

### Step 6 — Bundler switch to webpack + build/dev validation (the real gate)

v4 is incompatible with Next 16's default Turbopack (see Risk 1). Three changes
make webpack build it (verified):

1. **`next.config.ts`** — add `transpilePackages` for the five `@perspective-dev/*`
   packages, and a `webpack` callback that sets `resolve.extensionAlias`
   (`.js` → `[".ts", ".js"]`, so the dist's `src/*.js` refs resolve to the shipped
   `.ts`) and treats `perspective-(server|js|viewer).wasm` as `asset/resource`.
2. **`package.json` scripts** — pin `dev` to `next dev --webpack --port 3001` and
   `build` to `next build --webpack`.
3. Verify:

```bash
npm run build       # passes under webpack (the gate that fails under Turbopack)
npm run dev         # compiles under webpack ("Next.js 16.x (webpack)")
```

Then, in a live browser with the backend + data (the part not exercised by the
build, since unit tests mock Perspective out), confirm each viewer path renders:

- `CorrelationMatrix` (Datagrid plugin).
- `SignalLog` (Datagrid plugin).
- `LiquidityHeatmap` forced into Perspective mode — feed ≥ `perspectiveThreshold`
  (default 10000) rows, or lower the threshold — to exercise the Heatmap plugin.

Confirm the WASM asset serves, the worker initializes, and the grid/heatmap
render. This browser check is the one open item; record its outcome in ADR-031 and
update ADR-015's v3 dev-WASM limitation note (v4's asset is `perspective-js.wasm`).

### Step 7 — End-to-end (recommended)

```bash
npm run test:e2e
```

Add a minimal Playwright spec covering the three Perspective-backed components if
none exists, so the runtime WASM path has a regression guard that the mocked unit
tests cannot provide.

## 5. Troubleshooting

- **Turbopack build fails: `Module not found: Can't resolve ('null' | <dynamic>')`.**
  This is v4's runtime blob-URL `import()` worker boot, which Turbopack cannot
  handle. Switch to webpack as in Step 6 — Turbopack has no workaround.
- **Webpack build fails: `Can't resolve '@perspective-dev/viewer/src/ts/extensions.js'`
  / `column-format.js`.** The published dist references those by `.js`, but the
  package ships `.ts`. The `resolve.extensionAlias` (`.js` → `[".ts", ".js"]`) plus
  `transpilePackages` in Step 6's `next.config.ts` resolves and compiles them.
- **WASM 404 in dev (`Missing ...wasm`).** v4 serves `perspective-js.wasm` and
  `perspective-server.worker.js`. The `asset/resource` rule in Step 6 emits them;
  verify they are served and that the dynamic `import()` inside `useEffect` is
  preserved (client-side only). This was a known v3 issue (ADR-015); re-test whether
  v4 resolves it.
- **Theme/visual regressions.** v4 redesigned the theme system and ships theme
  files under `@perspective-dev/viewer/dist/css/`. If the viewer renders
  unstyled in the browser, import a theme explicitly (e.g.
  `import "@perspective-dev/viewer/dist/css/themes.css"`) at the component or
  layout level.
- **`"Heatmap"` plugin not found.** It must be imported from
  `@perspective-dev/viewer-charts` (not `viewer-d3fc`); the import in
  `LiquidityHeatmap.tsx` is what registers it.
